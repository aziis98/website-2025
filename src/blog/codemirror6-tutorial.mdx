Recently, I've been working on more and more complex web applications and one common component that many of these applications would benefit from is a small code editor. For now I've always used just simple textareas without any advanced features or syntax highlighting, but editors are a very important input (and output) device for many use cases.

There are many options to choose from when it comes to text editors for the web, here are some of the most popular ones:

- Simple **Textarea** (or an element with `contenteditable`) -- The most basic option, it is easy to add automatic resizing and supports copy-paste and undo/redo out of the box, but we cannot easily add advanced features like syntax highlighting, code folding, and autocompletion.

    If you only need a simple text input with autocomplete, HTML has the `<datalist>` element that can be used to provide suggestions for an `<input>` or `<textarea>` element.

- **Ace** -- A popular embeddable code editor with a rich feature set.

- **Monaco** -- This is the editor that powers VS Code, built by Microsoft.

- **CodeMirror** (versions 5 and below)

- **CodeMirror 6**

A notable mention is CodeJar, a lightweight editor library that uses "the overlay trick" to support syntax highlighting in a `contenteditable` element. It is very easy to set up and also provide custom syntax highlighting through Prism.js, Highlight.js or with a custom user provided function.

Most text editor libraries grew organically over time, adding features and complexity in an ad-hoc manner. CodeMirror 6 is the latest iteration of the CodeMirror project, a complete rewrite that was designed from the ground up with a modular architecture in mind that separates state management from rendering and command handling.

What's the motivation for this post? Many of the applications I worked on recently could benefit from AI code generation features. _The chat interface model isn't always ideal_; I prefer having LLMs update a document by regenerating it completely or using editing tools. In both cases, users **need to see the diff** between the old and new versions of the document and be able to accept or reject the changes.

For my use cases, this is currently the most intuitive and precise way to handle external changes while editing both code or prose.

CodeMirror already provides an extension called [codemirror/merge](https://github.com/codemirror/merge) that offers side-by-side and unified diff views, making it well-suited for this use case. In this article, we'll explore the basics of using CodeMirror 6 and how to leverage the merge extension to build a simple code review interface.

**TL;DR**: Here is a simple example of how to setup a CodeMirror 6 editor with the merge extension:

```ts
import { EditorState, EditorView, basicSetup } from 'codemirror'
import { unifiedMergeView } from '@codemirror/merge'

const state = EditorState.create({
    doc: 'one\ntwo\nthree\nfour',
    extensions: [
        basicSetup,
        unifiedMergeView({
            original: 'one\n2\nthree\n4',
            allowInlineDiffs: true,
        }),
    ],
})

const view = new EditorView({
    parent,
    state,
})
```

And if you want to update the current content of the diff editor programmatically, you can do as follows:

```ts
function searchAndReplace(editorView, searchText, replaceText) {
    const changes: ChangeSpec[] = []
    const regex = new RegExp(searchText, 'g')

    const docText = editorView.state.doc.toString()
    for (const match of docText.matchAll(regex)) {
        changes.push({
            from: match.index,
            to: match.index + match[0].length,
            insert: replaceText,
        })
    }

    if (changes.length > 0) {
        editorView.dispatch({ changes })
    }
}
```

## Basic setup

As most text editor libraries, CodeMirror 6 can be used with a very simple setup. Just provide a DOM element to mount the editor into and some initial content. Here is a minimal example from [the official documentation](https://codemirror.net/examples/basic/):

```ts
import { basicSetup } from 'codemirror'
import { EditorView } from '@codemirror/view'

const view = new EditorView({
    doc: 'Start document',
    parent: document.body,
    extensions: [basicSetup],
})
```

Differently from other editors, accessing and modifying the content of the editor is more involved than just reading or writing a property. To get the current content of the editor, you can use `view.state.doc.toString()`. To modify it programmatically, you need to dispatch a transaction with the changes you want to apply:

```ts
// Get current content
const content = view.state.doc.toString()
console.log(content)

// Replace all content
view.dispatch({
    changes: { from: 0, to: view.state.doc.length, insert: 'New content' },
})
```

## Core Concepts

Before diving deeper, let's understand three fundamental concepts in CodeMirror 6: the state, the view, and extensions.

- **State**: The state represents the current document, including its content, selection, and metadata. It is immutable and can be updated with transactions.

- **View**: The view is responsible for rendering the editor in the DOM and handling user interactions. It listens to changes in the state and updates the display accordingly.

- **Commands** are functions that perform specific actions in the editor, such as inserting text, deleting text, or moving the cursor. They can be triggered by user input (like keyboard shortcuts) or programmatically.

These are separated at the module level as well, with `@codemirror/state`, `@codemirror/view`, and `@codemirror/commands` packages.

## Monitoring Merge View Interactions

When using the merge view for code review or AI-generated changes, you often want to track user interactions—specifically when they accept or reject changes. CodeMirror 6's update listener system makes this straightforward.

The merge view emits user events when chunks are accepted or reverted. You can listen to these events using `EditorView.updateListener`:

```ts
import { getChunks, unifiedMergeView } from '@codemirror/merge'

const state = EditorState.create({
    doc: newContent,
    extensions: [
        basicSetup,
        unifiedMergeView({
            original: oldContent,
            allowInlineDiffs: true,
        }),

        // Listen for accept/revert events
        EditorView.updateListener.of(update => {
            const remainingChunks = getChunks(update.state)?.chunks.length

            const transaction = update.transactions.find(
                tr => tr.isUserEvent('accept') || tr.isUserEvent('revert'),
            )

            if (transaction) {
                const eventType = transaction.isUserEvent('accept')
                    ? 'accepted'
                    : 'reverted'
                console.log(
                    `Chunk ${eventType}! ${remainingChunks} chunk(s) remaining.`,
                )

                // You can trigger UI updates, analytics, or other side effects here
            }
        }),
    ],
})
```

The `getChunks()` function from `@codemirror/merge` gives you access to the current diff chunks, allowing you to determine how many changes are left to review.

The next step is to enable or disable the unified diff view based on the current state of the editor. For example, by default, you might want to show the classic editor view without the unified diff mode, and only enable it after an edit the user needs to review. We can achieve this by conditionally applying the `unifiedDiff` extension using **compartments**, which allow us to "reconfigure" parts of the editor configuration dynamically.

We can create a new "extension type" for this compartment as follows:

```ts
export const unifiedDiffCompartment = new Compartment()
```

Then we can instanciate this as empty using `unifiedDiffCompartment.of([])` in the initial editor configuration, and later reconfigure it to enable the unified diff view when needed:

```ts
view.dispatch({
    effects: unifiedDiffCompartment.reconfigure(enabled ? unifiedMergeView(...) : []),
})
```
